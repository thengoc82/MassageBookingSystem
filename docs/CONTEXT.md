This file is the single canonical domain source of truth. Read it first when starting any feature or clarifying terminology. `docs/adr/` holds Architectural Decision Records — check before proposing architectural changes. Update this file when introducing new domain concepts. Write a new ADR for significant architectural decisions.

## Core Entities

**Customer**
A person who books massage services, identified by phone number. Created automatically on first booking. Can be blocked via the NG List.

**Therapist**
Staff member who performs massage services. Assigned to exactly one Shop. Works according to Shifts. Can be requested by name for single-person Bookings only.

**Shop**
A branch location offering massage services. Has opening hours, Courses, Therapists, and receives Bookings.

**Course**
A massage service offered at a Shop. Two types: `main` (primary service) or `addon` (supplementary service). Has duration and price.

**Booking**
A confirmed service reservation. Contains 1+ people, each assigned one or more selected main Courses plus zero or more addon Courses. Has a unique booking code generated by the system.

**Shift** (full name: Therapist Shift)
A recurring weekly time block when a Therapist is scheduled to work (e.g., "Monday 08:00-17:00"). A Therapist can have multiple Shifts across the week.
`effectiveFrom` is the first date on which the Shift applies; a Shift has no end date. Admins may create, edit, and delete Shifts. Shifts for the same Therapist and weekday cannot overlap, even when their effective dates differ; adjacent time blocks are allowed. Editing or deleting a Shift is rejected if it would leave an assigned future `Booked` or `CheckedIn` Booking without a covering Shift.

**Customer Restriction** (also called "NG List")
A block preventing a Customer from making new Bookings. Placed by Admin with a reason. Can be active or inactive. Active restriction records determine managed blocks; inactive records retain history. Removing an entry deactivates it rather than deleting its record. `Customer.isBlocked` is synchronized for existing customer displays. Eligibility also honors a legacy flag-only block until the Task 6 data migration converts it to a restriction record.

## Lifecycle States

**Booking Status**
- `Booked` — confirmed, customer has not yet arrived
- `CheckedIn` — customer arrived, service in progress
- `CheckedOut` — service completed (terminal state)
- `Cancelled` — customer or admin cancelled (terminal state)

Valid transitions:
- `Booked` → `CheckedIn` → `CheckedOut`
- `Booked` → `Cancelled`

Only `Booked` status allows modification.

## Roles

**Admin**
System operator who manages Shops, Courses, Therapists, Shifts, and Bookings. Can check customers in/out. Can manage the NG List.
Admin accounts for local development are created by the command-line seed script
on an empty development database. There is no public demo-setup endpoint.

**Customer** (public role)
Person using the booking system. Booking creation requires no account. Viewing, editing, or cancelling existing bookings requires a short-lived access code for the booking phone; see [ADR 0004](adr/0004-phone-verified-booking-access.md). The development terminal provider supports local testing only and does not prove control of the phone.

**Booking access**
Booking access code verification issues a short-lived token scoped to the normalized phone. It grants access to that phone's bookings only. Booking code, booking ID, and phone number alone do not grant access. Admins may manage any booking; assigned therapists may view and check in/out their bookings, including group assignments. Only an admin or assigned therapist may check in/out a booking.

## Booking Flow (Optimistic Availability)

1. Customer selects a shop, date, guests, reserved duration, and (for one guest) any therapist, a therapist gender, or a specific therapist.
2. System returns available slots (capacity = active therapists on shift − overlapping bookings). A gender choice counts only eligible therapists of that gender; group choices require one distinct therapist per guest.
   With `show_therapists=true` it also returns the therapist list + per-slot `availableTherapistIds`.
3. Customer picks a valid time slot (optionally a specific therapist, e.g. via the dashboard Gantt).
4. Customer selects courses whose combined duration equals the reserved duration, then enters a phone number and optional special requests. A therapist selected on the schedule stays in booking context.
5. Customer confirms
6. System immediately calls `POST /api/bookings` — **no reservation hold**
7. If successful: booking code returned
8. If slot is gone (therapist taken by another booking during the flow):
   - System refreshes availability
   - Suggests nearby slots that satisfy the same guest count and therapist preference
   - Customer chooses again on the booking form without losing courses, contact details, or notes
   - The new choice is checked again on submission; a second loss follows the same recovery path

In chat, a one-guest customer can choose no therapist preference, an available gender, or a named therapist offered by Flask for the selected slot. The chatbot shows the complete draft and requires a final confirmation before calling Flask. Group bookings have no therapist preference. Chat lookup, modification, and cancellation use the same phone-scoped verification as the web flow; public creation does not require that token. A chatbot timeout after a write leaves the outcome uncertain until a verified lookup or staff assistance, and a similar older booking does not establish which request created it.

Availability is **optimistic** — shown as it was at query time. Creation rechecks therapist availability inside a database transaction. SQLite creation acquires a write transaction before reading availability; see [ADR 0003](adr/0003-atomic-therapist-assignment.md).

## Business Rules

### Customer
- Customer is identified by phone number. If new, auto-create on booking.
- Blocked customers (NG List) cannot create bookings.
- Admins may add a reasoned restriction for an existing Customer, edit its reason, or deactivate it. A new block after removal creates a new record. The same phone in local and `+84`/`84` forms shares eligibility; existing noncanonical phones retain exact matching. Restriction reasons and history are admin-only. Removing the last active restriction permits new valid Bookings but does not alter existing Bookings.

### Therapist Assignment
- **1-person booking:** Can request a therapist via `therapistPreferenceType` + `therapistPreferenceValue`
  (`specific` + therapist id, `gender` + `Male`/`Female`, or `no_preference`). The service rechecks
  that therapist's shift and availability at confirm time for `specific`.
- **Group (2+):** Cannot request a specific therapist or therapist gender. System assigns one distinct available therapist per guest, ordered by the fewest booked minutes on that date and then therapist ID.
- Therapist must belong to the same Shop as the Booking.
- Therapist must be on an active Shift covering the Booking time.
- Therapist must have no overlapping Booking.
- Slot capacity and creation use distinct active therapists with covering Shifts, excluding therapists occupied by overlapping `Booked` or `CheckedIn` Bookings. Occupancy includes per-guest assignments and the legacy `Booking.therapist_id` pointer without double-counting.
- A single Shift must cover the whole Booking interval. Changes to Shifts are serialized with booking writes for the same Shop; successful changes affect subsequent availability queries immediately.

### Service Assignment
Each person in a Booking receives the same sequence of 1 or more selected main Courses + 0 to N addon Courses. This preserves the existing multiple-main-course booking flow. The selected durations and prices can be submitted as `selectedCourses` in booking preferences because `services` contains only `personIndex` and `courseId`. For a single course, the reserved duration can identify its catalog option; for courses with one option, that option is unambiguous. Otherwise `selectedCourses` is required. Every submitted option must match the active course catalog. The selected durations sum to the reserved duration for each guest; total price is the per-guest course sum multiplied by guest count.

Public service discovery lists active Courses at open Shops only when they have at least one catalog option accepted by booking creation (`duration` is a positive integer and `price` is a nonnegative integer). A Course may have several duration and price options, including different prices for the same duration; clients retain the chosen pair. Slot availability depends on the selected date, total duration, guest count, and therapist shifts and bookings. It remains provisional until booking creation succeeds. The catalog has no service description field or stored booking total.

### Booking Modification
- Only `Booked` status bookings can be modified.
- The customer booking detail offers edits only after phone-code verification. Customers may change the date, start time, duration through a valid course selection, main courses, add-ons, and a one-guest therapist preference. Shop, guest count, phone, status, and saved notes are read-only in this flow.
- Every PATCH rechecks shop hours, active course options, shifts, and therapist availability in the local booking transaction, excluding the booking being edited. The public slot list includes the existing booking as occupied, so it is guidance rather than a final edit decision. No external POS modification adapter exists.
- Customer cancellation is available only while the booking is `Booked`. A concurrent check-in or cancellation can reject an edit or cancellation; the customer view refreshes the saved status.

### General Constraints
- Booking code is unique system-wide, format `BK{YYYYMMDD}{4digits}`.
- Course type must match: `main` for primary services, `addon` for add-ons.
- Shop must be open at the selected time.
- Booking date cannot be in the past; duration and guest count must be positive. The entire booking must fit inside one day's shop hours.
- Each person in a booking gets the selected main courses + 0..N add-ons.

## Terms NOT in Use

- "Appointment" — we say Booking
- "Service Provider" — we say Therapist
- "Package" — we say Course (can be main or addon type)
- "Branch" — we say Shop
- "Time Slot" — no longer a stored entity, availability is calculated dynamically from therapist shifts and bookings
- "Wait list" — not supported
- "Reservation" — removed. No time-limited holds. See ADR 0002.
- "Membership tier" — we track member_rank (Silver/Gold/Platinum) but it's not used in booking logic yet
